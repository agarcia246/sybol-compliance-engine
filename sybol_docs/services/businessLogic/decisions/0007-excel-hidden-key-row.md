# ADR-0007: Excel Technical Key Encoding via Hidden Row

**Status:** ✅ Accepted  
**Date:** 2026-03-19  
**Deciders:** Engineering Team  
**SPEC sections:** FR-10, FR-11, FR-12  

---

## Context and Problem Statement

The Excel template generated by `downloadClaimsTemplate()` contains column positions that map to claim fields (e.g., column C = `fullName`, column D = `birthDate`). The claim column structure is dynamic — it depends on the catalog document's schema, which can vary per credential type and tenant.

The parser lambda receives only the Excel file (identified by its S3 key). It must reconstruct the mapping of Excel column → claimKey without:
- Accessing the database (the parser is stateless).
- Receiving additional metadata in the S3 trigger event (S3 events carry only bucket + key + size).
- Relying on a fixed schema or hardcoded column order.

Therefore, the mapping must be embedded directly in the Excel file at template generation time.

---

## Decision Drivers

- The template generator (`excelGenerator.js`) already knows the `claimKeys` at generation time (it receives the catalog document's claim schema).
- The parser is a Lambda triggered by S3 event; it cannot query an API or DB without credentials.
- The solution must be invisible to end users (does not interfere with data entry UX).
- Must be robust: if the user re-saves the file in Excel/LibreOffice, the hidden row must be preserved.
- The solution must not require any external configuration file or lookup table.

## Current Template Row Structure

| Row | Purpose | Visible |
|-----|---------|---------|
| 1 | Title / credential name | ✅ |
| 2 | Instructions text | ✅ |
| 3 | *(was empty — repurposed)* | — |
| 4 | Column headers (human-readable labels) | ✅ |
| 5 | Example data row | ✅ |
| 6+ | User data rows | ✅ |

## Considered Options

### Option A — White text on white background in Row 3
- Cell font color `#FFFFFF`, background color `#FFFFFF`.
- The keys appear invisible to users on screen.
- **Pros:** No special Excel feature required.
- **Cons:** Text is visible when the cell is selected or copy-pasted. Identified by the team as a poor-quality approach ("cutrada"). Does not survive copy-paste to another spreadsheet. Not accepted.

### Option B — Separate JSON sidecar file stored alongside Excel in S3
- The template generator uploads a companion `{processId}.json` to S3 alongside the Excel file, containing the key mapping.
- The parser downloads both files.
- **Pros:** Clean separation of data and metadata.
- **Cons:** Requires the parser to make an S3 `GetObject` call for the manifest (additional latency and IAM permission), increases deployment complexity, orphaned manifest files if the process fails before cleanup. Rejected by the team.

### Option C — ExcelJS cell metadata / named ranges
- Use ExcelJS named ranges or custom defined names to embed the mapping.
- **Pros:** Proper Excel metadata, preserved through file saves.
- **Cons:** ExcelJS support for named ranges is limited; cross-library compatibility (LibreOffice) is unreliable. Not chosen.

### Option D — Hidden row (Row 3) with technical keys (chosen)
- The template generator writes the technical `claimKey` value for each dynamic column into the corresponding cell in Row 3 (same column as the label in Row 4).
- The `documentId` is also written in the fixed column slot reserved for document identification in Row 3.
- Row 3 is then hidden: `worksheet.getRow(3).hidden = true`.
- In Excel and LibreOffice, hidden rows are preserved when the file is saved. The row remains hidden when re-opened.
- The parser reads Row 3 as the key mapping, then reads Row 6+ as data.
- **Pros:** Standard Excel feature; visible in "unhide rows" if inspected; survives save/re-open; zero external dependencies; self-contained file.
- **Cons:** Visible to technically savvy users who explicitly unhide rows — acceptable, it's metadata not sensitive data. No cons in practice for the intended use case.

---

## Decision

**Option D** — hidden Row 3 with technical keys.

### Template generation change (`excelGenerator.js`)

```js
// Row 3: technical keys (hidden)
const keyRow = worksheet.getRow(3);
keyRow.getCell(1).value = documentId;            // fixed: col A = documentId
keyRow.getCell(2).value = 'subject_did';         // fixed: col B = recipient DID
keyRow.getCell(3).value = 'init_date';           // fixed: col C
keyRow.getCell(4).value = 'expiration_date';     // fixed: col D
claimSchema.forEach((claim, i) => {
  keyRow.getCell(5 + i).value = claim.key;       // dynamic: cols E+
});
keyRow.hidden = true;                            // hide from user
```

### Parser reading change (`s3ParserHandler.js`)

```js
const keyRow = worksheet.getRow(3);
const documentId = keyRow.getCell(1).value;
const columnMap = {};                            // colIndex → fieldName
keyRow.eachCell((cell, colIdx) => {
  if (cell.value) columnMap[colIdx] = cell.value;
});
// columnMap: { 1: 'documentId', 2: 'subject_did', 3: 'init_date', ... }
```

---

## Consequences

- **Positive:** The Excel file is fully self-describing — no external lookup needed.
- **Positive:** Hidden rows are a standard, stable Excel feature preserved across save/re-open/email.
- **Positive:** Technical metadata is inspectable (unhide) without corrupting data.
- **Negative:** If a user opens the file, manually unhides Row 3, and modifies the key values, the parser will produce incorrect field mappings. This is considered an intentional mis-use case outside the system's responsibility.
- **Neutral:** Row 3 was already structurally empty in the existing template, so this is a backward-compatible repurposing.
