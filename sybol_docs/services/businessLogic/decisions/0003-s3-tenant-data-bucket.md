# ADR-0003: S3 Data Bucket with Tenant Prefix Segregation

**Status:** ✅ Accepted  
**Date:** 2026-03-19  
**Deciders:** Engineering Team  
**SPEC sections:** NFR-20, NFR-21, NFR-22, FR-20  

---

## Context and Problem Statement

The Batch Credential Import pipeline requires a place to store uploaded Excel files before they are processed asynchronously. The system serves multiple tenants using shared Lambda infrastructure. The key question is: **how should S3 storage be structured to guarantee tenant isolation while minimising operational overhead?**

Three concerns must be balanced:

1. **Isolation**: Tenant A must not be able to read or write files belonging to Tenant B.
2. **Simplicity**: Onboarding a new tenant should not require creating new AWS resources.
3. **Cost and maintenance**: Minimise the number of S3 buckets to manage.

The existing platform already uses one bucket (`sybol-statics`) for static frontend assets, which is a different concern and must not be mixed with operational data.

---

## Decision Drivers

- Strict multi-tenant data isolation is a hard requirement.
- Tenant IAM roles already exist per tenant (created at onboarding via `ClientInfraStack`).
- The Cognito Identity Pool is used by the frontend to obtain temporary AWS credentials tied to the tenant's IAM role.
- S3 IAM policies support resource-level restrictions including path prefixes.
- New S3 buckets require CloudFormation/CDK changes and manual configuration steps per tenant.

---

## Considered Options

### Option A — One bucket per tenant
- Create `sybol-data-{tenantId}-{env}` per tenant.
- Each tenant has full access to their own bucket.
- **Pros:** Strongest isolation boundary; easiest IAM policy.
- **Cons:** Requires a new bucket per tenant onboarding (CDK change, manual steps); high operational overhead at scale; S3 soft limit of 100 buckets per account.

### Option B — Shared bucket with tenant prefix segregation (chosen)
- Single bucket `sybol-data-{env}`.
- Each tenant reads/writes only to `{tenantId}/batch-imports/*`.
- IAM policy on tenant role restricts `s3:PutObject` to `arn:aws:s3:::sybol-data-{env}/{tenantId}/batch-imports/*`.
- System actors (parser Lambda) have `s3:GetObject` on the full bucket.
- **Pros:** No new bucket per tenant; isolation enforced by IAM; simple onboarding (add IAM policy statement to existing role).
- **Cons:** Slightly more complex bucket policy; accidental misconfiguration of IAM could theoretically allow cross-tenant access (mitigated by explicit deny).

### Option C — Presigned URL flow with API Gateway controlling S3 access
- Backend generates a presigned URL per upload, restricting the key to the correct tenant prefix.
- Frontend uses the presigned URL directly.
- **Pros:** No need to distribute IAM credentials to frontend.
- **Cons:** Presigned URLs expire; require a backend round-trip before every upload; the frontend already has `CognitoService.uploadToS3()` using Cognito Identity Pool credentials, making this redundant.

---

## Decision

**Option B** — shared bucket `sybol-data-{env}` with tenant prefix segregation enforced by IAM.

The frontend uploads directly using `CognitoService.uploadToS3()` with Cognito Identity Pool credentials bound to the tenant's IAM role. The IAM role policy restricts `s3:PutObject` to the tenant's own prefix. A cross-tenant write is therefore impossible by IAM policy, not by application logic.

The S3 key pattern is:
```
{tenantId}/batch-imports/{processId}.xlsx
```

The `processId` is generated by `POST /api/bl/batch` before the upload, ensuring the backend controls the key structure.

---

## Consequences

- **Positive:** No new AWS resources per tenant onboarding. Tenant isolation is enforced at the IAM layer, independent of application code.
- **Positive:** The parser Lambda can read any file in the bucket using its execution role, without needing per-tenant credentials.
- **Positive:** S3 lifecycle rules on prefix `*/batch-imports/` can auto-delete files after 30 days without tenant-specific configuration.
- **Negative:** The IAM policy statement for `s3:PutObject` must be added to every tenant role at onboarding and documented in `GUIA_OPERATIVA_MULTI_TENANT.md`.
- **Negative:** A bucket-level misconfiguration (e.g. removing BlockPublicAccess) would affect all tenants simultaneously. Mitigated by SCPs and bucket policy.
